# Notes for coding agents

- Node >= 24 runs the TypeScript directly in development (no build step to run tests or the CLI). Runtime dependencies: none. Imports use `.ts` extensions; no `enum`, no parameter properties (`erasableSyntaxOnly`). `esbuild` and `postject` are dev dependencies, used only to build the executable.
- Package: `npm run build` emits `dist/` (JS + types; Node cannot strip types under `node_modules`). `npm run check:package` installs the tarball into an empty project; run it when you change `exports` or entry points. Consumers can only import `./ibt`, `./model`, `./replay`, `./chart`, `./metrics`, `./testing`. The app (`src/app/`) is not an entry point.
- The pages' scripts (`src/chart/client.ts`; the strings in `src/app/page.ts` and `src/app/workbenchPage.ts`) are embedded verbatim: no backticks, no dollar-brace, no closing script tag, no `innerHTML`; channel names and file text are untrusted, so use `textContent`. Their behaviour is exercised only in a simulated DOM (jsdom), so say so if you change a layout and have not looked at it in a browser.
- Test: `npm test`. Types: `npm run typecheck`. Format: `npm run format:check`. Executable: `npm run build:exe` (the _Windows executable_ workflow builds and runs it).
- Never add or commit `.ibt`, `.irdt` or any real recording. Fixtures are built with `src/ibt/testBuilder.ts` (see `tests/helpers/syntheticIbt.ts`). Keep files under 512 KB (CI refuses larger ones); the golden file is gzipped.
- `src/model/` must stay pure: relative imports that stay inside it. `tests/boundary.test.ts` checks it.
- The model: `src/model/irdashies/` (four files) is copied from irdashies at a pinned commit and must not be edited by hand (`npm run vendor -- --check`, `tests/vendor.test.ts`). `src/model/surface/TireSurfaceModel.ts` is a fork and the lab's own; with its default constants it must equal the overlay's numbers. `tests/overlay-equivalence.test.ts` compares the model with the real overlay processor's output (`tests/golden/processor.json.gz`, made by `scripts/goldenProcessor.cjs` from an irdashies checkout at the pinned commit). If that test fails, the model changed; do not regenerate the golden file to make it pass without saying why.
- `src/model/tuning.ts` lists the model's components and numbers. If you change a constant's meaning or add one, change its description and test; a test checks that running with every registry default equals running with none.
- Do not invent channel names, units or semantics. If it is not in `channels/channels.yaml` as `verified`, say it is unverified and ask for a real file. The lap channels, the surface temperatures, the wear channels in a real `.ibt` and the iRacing recording switch have not been seen working against real data.
- Do not claim the model reproduces iRacing's tire physics. It is the overlay's empirical estimate. The workbench shows how that estimate responds, not how the game does.
- The program sends a command to a running game (telemetry start or stop) and opens files on request: the local server needs its token, the loopback Host and a JSON POST with the token header (see `src/app/server.ts` and its tests). Do not weaken any of them.
- Parts of `src/ibt/` and the model are adapted from irdashies (MIT); keep the provenance headers and `NOTICE`.
- Reports (`src/app/report.ts`): a report carries the model's inputs as plain numbers, the session summary (car, track, track length and temperatures: fields taken by name in `summarizeSession`), the file's channel list with the sim's descriptions, and what the user typed. It must hold no driver names, ids or iRating, no path and no recording; `tests/report.test.ts` puts such text in a recording and checks. Do not add fields without checking that, and keep the preview showing everything saved. Add a column in `FIELDS`; `readReport` treats a report as hostile input and refuses columns it does not know.
